Octopushy backend and agent review

13 November 2026, at commit a860484 on t3/backend-agent-review. Scope is backend/, agent/, contracts/ and deploy/. The frontend is out of scope except where it drives server load.

The design is sound and I would keep it. The rules that matter for a tool that owns every deployment are already in the code. A change is never retried or interrupted, a lost agent means "uncertain" and never "failed", the approved plan is checked by hash before it is applied, and results survive a restart on both sides. I found no critical hole.

What needs work is how the system behaves on a bad day. One lock covers too much, so a slow git push can make healthy work look lost. One run that throws stops every other run. Run history, logs and artifacts are never deleted. And one path lets a commit to the lab repository send a stored secret to a host the commit chooses. Fix those, then do one structural refactor before adding the next executor or stage type.

System map, with where the problems are

  • 1The backend fetches whatever workflows repository the newest commit names, with whatever store key that commit names, before anyone validates the commit. Partly closed in this pass.
  • 2One lock serializes ticks, heartbeats, results, git pushes and some GET requests. One exception in one run ends the whole pass.
  • 3A result that throws while it is recorded drops the stream, and the agent replays the same result on every reconnect.
  • 4Runs, attempt logs, saved plans and secret-release rows are kept forever.
  • 5The agent follows symlinks a tool leaves behind, and the shipped image runs tools as the agent's own user. A running change cannot be stopped, OpenTofu has no time limit, and a result over 64 MiB blocks the channel.
  • 6Forwarded headers were trusted on both ports. Fixed in this pass. Bodiless POST endpoints have no origin check.

Do first

Ranked by what I would fix before trusting this with everything. Each names the smallest change that removes the problem. A filled dot means I read the code path myself. A hollow dot means one reviewer reported it with file references and I did not re-trace it.

1. Decide who may point the server at a workflows repository

High, securityHalf a dayPartly fixed● read

RepositorySync reads workflows.repository and workflows.credential.store from the newest commit's octopushy.yaml and fetches at once, before the revision is validated. The askpass helper answers any password prompt with the secret. So a commit can still name any key outside system/, such as a Proxmox token, and an https:// URL of its choosing, and the next poll sends that token there as Basic auth.

ADR 0002 accepts that repository code runs with credentials. This is a different thing. It needs no run, no approval and no installation trust, and it reaches keys the commit's own guests were never given. Your threat model is one operator, so the realistic causes are a compromised Git account or a bad merge.

The fix is the pattern you already have for Proxmox endpoints. Record the pair of URL and key an operator confirmed, fetch only that pair, and show "Waiting for trust" when a commit changes it. Also refuse file:// and absolute paths from the repository unless a server setting allows them, since those make the server read any Git repository it can reach on its own disk.

2. Contain a failure to the run it belongs to

High, reliabilityHalf a day● read

RunEngine.TickAsync advances every active run in one loop with no catch, oldest first, and Orchestrator wraps the tick and every scheduling phase in a single try. If run N throws, runs after it are skipped, so are configure and pipeline scheduling, agent updates, observations and cron. The same run throws again five seconds later. Dispatch has the same shape. It catches a named list of exception types, and anything else, such as a missing key in context.Secrets, ends the pass. Attempts already saved as assigned in that pass are never sent, and after 60 seconds the changes among them are uncertain.

The agent stream has the twin problem. AgentChannelService.Connect catches cancellation and IOException only. If OnResultAsync throws, the stream ends, the agent reconnects, sends the same result first, and it throws again.

Give each run its own scope and a catch that writes the error to run.Detail. Give dispatch a catch-all per attempt that fails that attempt only. Give each phase in Orchestrator its own try. In Connect, catch per message, do not acknowledge a result that failed to record, and after a few tries settle the attempt as uncertain with "the result could not be recorded".

3. Take slow work out from under the engine lock

High, reliabilityAn hour, then half a day● read

Details and a diagram are in the next section. In short, ChangeService.CommitAsync pushes to Git inside engine.ExecuteAsync, each git command may take five minutes, heartbeats wait for the same lock, and leases last 60 seconds. A slow push makes every running change look lost.

4. A stop that stops, and a time limit for OpenTofu

High, operationsHalf a day● read

The agent refuses CancelAttempt for a running change, which is right as a default. But Force stop in the UI sends that same cancel, marks the attempt uncertain and moves on, while the tool keeps running and keeps its slot on the agent. tofu apply has no time limit and its heartbeats renew the lease for as long as it hangs. Ansible has timeoutMinutes, OpenTofu does not. Today the only way to end a provider stuck on a Proxmox task is to kill the agent.

Add force to CancelAttempt behind a capability. On a forced cancel send OpenTofu SIGINT, which makes it finish the resource in flight and save state, then SIGTERM after a grace period. The outcome stays uncertain and carries the state. Add timeoutMinutes to the opentofu input with the same timer Ansible uses.

5. Never queue a result the channel cannot carry

High, reliabilityUnder an hour● read

The gRPC limit is 64 MiB each way. Nothing compares a finished AttemptResult with it. Captured stdout may reach 512 MiB (tools/mod.rs:32), state may be 32 MiB, and the saved plan has no cap. A result over the limit fails to encode, the stream errors, the agent reconnects, and collect sends the same result first again. Everything behind it waits forever.

In AttemptManager::finish, measure the encoded size. Over the limit, drop outputs and the plan, keep the state if it fits, and store uncertain for a change or failed for a read, with "result too large". Lower MAX_CAPTURE to 64 MiB and fail at the cap, since today it truncates without saying so.

6. Retention for runs, logs and artifacts

High, after monthsHalf a day● read in part

Uptime, observations, state versions, images and git snapshots are all bounded already. Runs, steps, attempts, their log files, saved plans under artifacts/ and secret_resolutions rows are not. ArtifactStore has no delete at all. The polled endpoints sort and scan these tables, so the cost shows up as latency before it shows up as disk.

Add a daily job that keeps, per resource, the last 50 finished runs or 180 days, and always keeps unfinished and uncertain runs and any run a change or schedule points at. Delete the attempt rows, log file, artifact directory and secret-release rows together. Add the missing foreign keys and indexes first, listed under performance and data, or the job has to cascade by hand.

7. Keep tool code away from the agent's own files

High, securityHalf a day, then days● read

Two separate holes lead to the same place, the agent's private key and other stacks' state.

First, the agent follows symlinks a tool leaves behind. After tofu plan and tofu show exit, the agent reads out/plan.bin and .terraform.lock.hcl with a plain fs::read (executors/opentofu/mod.rs:501-504) and packs them into the plan artifact. The tool image is named by the workflow, so repository code controls what runs. If it swaps either file for a symlink to /var/lib/octopushy-agent/key.pem, the agent reads the host file from outside the container and ships it. The apply step then unpacks that artifact into a workspace the same image can read. The archive extractor's symlink checks are thorough, but they cover what arrives, not what a tool writes afterwards. This works with podman and docker too, so it defeats the sandbox. The second reviewer found it and I confirmed the read sites. Fix: open every file a tool wrote without following links and require a regular file inside the workspace. The same goes for the state file, the Nix lock and Ansible's prepared document.

Second, the agent image starts with --tool-runtime local (agent/packaging/container-entrypoint.sh), and that is what the compose stack and the Proxmox installer run. In that mode OpenTofu, Ansible and Nix run as the agent's own user with a cleared environment and nothing else between them and the agent. Code that runs during a preview, with only the read-only token, can read the agent's key, the outbox, a neighbouring workspace, and the environment of an apply running beside it, which holds the write token. agent/README.md still calls this mode "for development and tests".

The safety boundary document accepts that hostile code can use the token it was given. It does not accept a step from the read-only token to the write token, or theft of the agent's identity. Interim: cap concurrency at 1 for the local runtime and correct the README and executors.md. Proper fix: start the container as root, keep state readable by root only, and drop each tool to its own unprivileged user before exec.

8. Refuse a second server process

Medium, reliabilityUnder an hour● read

Runs, steps, attempts and OpenTofu state have no row version and no conditional update. Only store entries carry concurrency tokens. All correctness comes from one in-process semaphore. That is a fine choice for one server, and simpler than the FOR UPDATE SKIP LOCKED queue the architecture agreement describes. But nothing enforces one server. Two containers during a botched update would both dispatch the same apply. Take a PostgreSQL advisory lock on a dedicated connection at startup and do not start the orchestrator or the agent channel without it.

The engine lock

RunEngine._gate is a single semaphore. Every write to a run goes through it, which is why I found no interleaving that corrupts a run. I would keep that. The problem is what else waits behind it.

Left: what queues behind one slow holder today. Right: the lock keeps its job, deciding state transitions one at a time, and the slow work moves out.

The sequence that hurts, with the default settings. At T+0 you save a change in the UI and the push holds the lock. At T+5 the tick queues. At T+10 each agent's heartbeat queues behind the tick. The push returns at T+70. The tick goes first, and every lease is now older than 60 seconds. Every running change becomes uncertain and every read-only step gets a second copy while the first still runs. A late result repairs it, unless you close the run first, and then an apply that succeeded is recorded as failed.

The one-hour fix is to stop heartbeats from needing the lock. OnHeartbeatAsync is two ExecuteUpdate statements that are safe on their own scope. The half-day fix moves git network work behind its own lock. ChangeReconciler relies on pushes holding the engine lock today, so it has to take the new one too.

The state machine as built

Names are the strings in AttemptStatuses and RunStatuses. A read-only attempt whose lease runs out gets a retry instead of "uncertain". A step follows its newest attempt. An uncertain run goes back to running when the late result arrives, or to failed when you close it.

The agent

The agent is the stronger half. Tar extraction refuses absolute paths, parent segments, links through earlier symlinks, devices and duplicates. The outbox writes a temp file, syncs, renames and syncs the directory. Recovery treats an unreadable marker as uncertain. Ansible gets secrets on stdin only and its key through a private ssh-agent. I would not restructure any of that.

  • AThe attempt is saved as assigned before the message is written to the stream. If the stream drops first, a change ends uncertain even though it never ran.
  • BNo time limit for OpenTofu, and a running change cannot be stopped. Item 4 above.
  • CThe heartbeat waits for the engine lock. Item 3 above.
  • DNo size check against the 64 MiB limit, and unacknowledged results go first on every reconnect. Item 5 above.
  • EAn exception while recording drops the stream and the agent replays the same result. Item 2 above.

Second opinion

A second model reviewed security on its own, with no sight of the other findings. It reached the workflows credential path independently and rated it critical. I rate it high because ADR 0002 already treats whoever can push as trusted to run code, but we agree on the fix. It also reported the log append, the bodiless POSTs and the forwarded headers, which matches the first reviewer. It added two things nobody else had. The symlink read is now part of item 7. Its other point is about the trust model, not a bug. Since ADR 0002, permission to push to the lab branch or to move a workflow release tag is permission to run code with an installation's token, before any apply approval. That is your documented choice and it is reasonable for one operator. It does mean the Git host is part of the control plane. Protect the tracked branch and the release tags there today, which costs nothing, and treat a second person with push access as a second operator.

Refactors, in order

The code has almost no dead weight and the tests pin behaviour through HTTP and a fake agent, so they will carry these refactors. Two things will slow you down if left alone. The meaning of a step is spread over name switches in about 15 files, and the JSON contract between backend and agent is written by hand on both sides with nothing that checks one against the other.

1. A step-type registry and explicit run kinds

AssignmentBuilder.ActionFor, TokenFor and SecretsFor switch on step names, more than 20 of them. RunEngine.ApplyEffectsAsync is a 140-line switch on the same names. The run kind is never stored. The code infers it with context.Stages is not null ? pipeline : context.Ansible is not null ? configure : provision, in three places. Your own migration document lists this as its phase 6 and measures 2,000 to 5,000 backend lines per feature. That number is the cost of this shape.

Do it in five steps, one pull request each. Store RunContext.Kind. Turn the three static switches into registry data, which is mechanical and the tests prove it. Move the three approval deciders behind a run-kind interface. Move effects one step family at a time, starting with the ones that hold no safety-boundary logic. Move image builds and observations into their own folders. The risk sits in the effects, which bind guests and restore protection, so that is where to go slowly. Effort is days. Do it before the next executor or stage type, not after.

2. One checked contract between backend and agent

The backend builds executor inputs with new JsonObject in 26 places and reads outputs through string indexers in about a hundred. The agent emits with json! in 46. The contract is 567 lines of prose in executors.md. Backend tests invent the agent's outputs by hand, so each side is tested against its own assumptions. Rename a field and every test stays green while production breaks. The one test that crosses languages, tests/e2e, is not in CI.

Start cheap. Add contracts/agent/v1/examples/ with one input and one output file per action. A Rust test deserializes each input into the agent's structs and checks each output builder against the example's keys. A backend test does the reverse, and FakeAgent.Plan loads the example. That is half a day and catches drift from then on. Typed records on the backend can follow.

3. Stop keeping state in prose

A superseded run is recognised by Detail.StartsWith("Superseded by "). Schema issues are filtered by Message.Contains("(workflow "). Decisions and policy values are string literals. Rewording a message changes behaviour. Add Run.EndReason, an issue source field, and constants. One migration, a few hours.

4. A test suite that stays fast

All 42 server test classes share one xUnit collection, so they run one after another, and 347 calls to ServerHarness.StartAsync each create a database and run every migration. The suite took 12 and a half minutes on this machine, against a 20-minute limit in CI, and it grows with every feature. Migrate one template database and create each test's database from it, then let classes run in parallel. Each test already owns its database.

5. Slices in place of Api/

Views.cs holds every page's read model and Endpoints.cs holds 47 routes. Changes, Icons, Uptime and Agents all depend upward on Api for DTOs. Follow the split you already made for changes, icons and state. Move runs, agents, variables and inventory into their own folders with their endpoints, views and DTOs. Do this after refactor 1 so the orchestration files move once.

6. One source of truth for versions and toolchains

A release touches eight files and nothing checks the tag against them. backend/Containerfile builds with the floating sdk:10.0 image while CI tests with the pinned SDK. There is no rust-toolchain.toml, no Dependabot, no dotnet format check. Add a release script, a CI check that the tag matches, and the pins.

Worth keeping

These are the parts I would defend in a refactor. Most of them are rules, and rules are easy to lose when code moves.

  • A change is never retried and never interrupted. A lost lease means uncertain, a person closes it, and one late result may still settle it (RunEngine.Agents.cs ExpireLeasesAsync, attempts/mod.rs cancel).
  • One writer for runs. Keep the lock, shrink what it covers. Do not replace it with row versions.
  • The approved plan is checked three ways before apply, and the plan's state version must still be the head (AssignmentBuilder.cs:393-433, TofuStateStore.cs).
  • OpenTofu state in the database with a lock owned by an attempt, lineage and serial checks, and snapshots during apply.
  • The agent's outbox and recovery, including the order in which the marker and the outbox entry are removed on acknowledgement.
  • Envelope encryption with the key name and version bound into the authenticated data, and the system/ scope kept away from every operator endpoint (Store/Envelope.cs, VariableStore.CheckUserKey).
  • Agent identity. The server sets the certificate subject, the agent pins the CA fingerprint from its enrollment token, and every RPC checks the serial against the database.
  • Masking that fails closed. The server withholds outputs whole when it does not know every secret the attempt held.
  • The hardened git wrapper and the agent's tar extraction. Both treat repository content as hostile already.
  • The test harness. Real PostgreSQL, a real Git repository, the real HTTP API and a fake agent on a real session. 1,128 backend test cases and 255 in the agent.
  • CI that fails on OpenAPI drift, generated-client drift and model-versus-migration drift, with actions pinned by SHA and audits on all three ecosystems.
  • CONTEXT.md with its "avoid" entries, and the ADRs. Few projects this young have a vocabulary this exact.
  • Octopushy.Definitions as its own project, shared by the server, the offline validator and CI.

Not worth doing

  • Squashing migrations. SchemaHistory refuses a database that records an id the assembly does not know, so a squash would lock out every existing install. The 26,000 Designer lines cost build time only.
  • Typed protobuf messages per executor. Example files give the check for a tenth of the churn.
  • Chunked transfer for repository files, or several streams per agent. 64 MiB on a LAN is enough once the size guard exists.
  • Automatic rollback, canaries across guests, Ansible check mode. Your docs explain why not, and I agree for one operator.
  • Removing reachability routing. It pays off with a second site. Add the single-candidate shortcut instead.

Method and limits

I read the spine myself: the proto contract, Program.cs, AgentServices.cs, RunEngine.cs and RunEngine.Agents.cs, the orchestrator, and on the agent connection.rs, run.rs, attempts/mod.rs and tools/mod.rs. Five reviewers then worked in parallel on backend security, agent security and robustness, orchestration correctness, performance and data, and architecture and tests, plus one on how to make the executors better. A sixth, on a different model, did an independent security pass and found the symlink read in item 7. I re-read the code behind every item in "do first" and behind everything I changed. Findings marked with a hollow dot come from one reviewer with file references that I did not re-trace.

Nobody ran an exploit or a load test. The credential path, the lock sequence and the oversize result are established by reading the code, not by reproducing them. Line numbers refer to commit a860484 and have shifted by a few lines in the files I edited.
